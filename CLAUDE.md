# CM Ear Wax Removal — project notes for Claude Code

See [README.md](README.md) for full architecture, tech stack, and setup details. This file covers conventions and automation specific to working in this repo with Claude Code.

## Skills

### `/seo-sync` (covers SEO **and** LLM/AI search)

Defined in `.claude/commands/seo-sync.md`. Decides whether the traditional SEO files (`index.html` JSON-LD, `docs/sitemap.xml`, `docs/robots.txt`) **and** the LLM/AI search discovery file (`public/llms.txt`) are out of sync with `src/App.tsx` (the source of truth for services, prices, and coverage areas), and fixes them if so. `llms.txt` is what AI assistants (ChatGPT, Claude, Perplexity, etc.) read to summarize the business when answering user questions — it needs the same attention as classic SEO. If nothing has drifted, it says so rather than making needless edits.

**Run this before every push to `main`.** A `PreToolUse` hook (`.claude/settings.json`) fires automatically when a `git push origin main` command is about to run and reminds to run `/seo-sync` first, so SEO fixes land in the same deploy rather than a follow-up one.

## Git workflow

- Work on `dev`. Merge to `main` only to deploy — GitHub Pages serves `docs/` from `main`.
- Never commit directly to `main`.
- **Before merging `dev` → `main`, check Supabase's Advisors** (Database → Advisors, or `get_advisors` via the Supabase MCP if the connected account can see this project) for new Security/Performance findings — any migration or policy change since the last deploy can introduce one silently (e.g. a new `SECURITY DEFINER` function without a pinned `search_path`, an overly-permissive RLS policy). Triage each finding: fix it, or note in this file why it's accepted as-is (see "Security review" below for the reasoning style to follow).
- **Before merging `dev` → `main`, also check GitHub Dependabot alerts** (`gh api repos/mobile-massage/cm-earwax-removal/dependabot/alerts --jq '.[] | select(.state=="open")'`, or the repo's Security tab). Fix what's reasonable to fix — for a devDependency-only finding, check first whether the flagged package is actually used (`pnpm why <package>`) before assuming it needs a version bump; if it's unused/vestigial, removing it outright is cleaner than patching a dependency nobody calls. Alerts are computed from `main`'s dependency graph, so they won't clear until the fix actually lands there.

## Build/deploy gotchas

- **Never delete old hashed JS/CSS files from `docs/` in the same deploy that replaces them.** GitHub Pages' CDN caches `index.html` for up to 10 minutes (`cache-control: max-age=600`), so some visitors can still be served an HTML shell referencing the *previous* build's hashed filename after you've pushed. If that old file has been deleted, they get a blank white page (script 404s, nothing renders, no console error). This actually happened once — see commit history around "Use relative paths for hardcoded image references" for the fix (restored the deleted files from git history). Instead: copy `*.js`/`*.css` from `bundle-out/` into `docs/` **without removing anything first**, and only prune genuinely orphaned old hashed files in a *separate*, later deploy once you're confident no cached HTML still points at them (a day or more later is safe).
- After copying, update `docs/version.json` with the new main-bundle hash so the auto-refresh polling picks up the deploy for users already on the page.
- `public/` and `docs/` versions of `robots.txt`, `sitemap.xml`, `llms.txt`, and `CNAME` must be kept in sync manually — there's no build step that copies them. If you edit one, edit both. `docs/CNAME` (containing `cmearwaxremoval.co.uk`) is what tells GitHub Pages to serve the custom domain — never delete it or the custom domain mapping breaks.
- The site is built with `--public-url "./"` (relative), not `"/"` — this lets the same `docs/` build work both at a GitHub Pages project subpath (`mobile-massage.github.io/cm-earwax-removal/`) and at the real custom domain root once attached. Don't change this back to `"/"` unless the project subpath is no longer needed.
- `logo-badge.png`, `favicon.png`, `apple-touch-icon.png`, `og-image.jpg`, and the service/about photos are referenced via plain string paths (`<img src="logo-badge.png">`, no leading slash), not JS imports — Parcel's asset graph never sees them, so they don't get hashed or auto-copied, and they must stay relative (no leading `/`) for the same subpath-compatibility reason above. Copy them from `public/` to `docs/` by hand on every deploy that touches them. The `og:image`/`twitter:image` **meta tags** are the one exception — those must stay full absolute URLs (`https://cmearwaxremoval.co.uk/og-image.jpg`) since they're read by external crawlers, not resolved relative to the page.

## Pricing is not displayed publicly

Real prices exist (£65 flat fee for ear wax removal regardless of method, £25 consultation-only if nothing needs removing) but the site deliberately shows "Contact me" / "get in touch" instead of the numbers in `src/App.tsx`, `index.html`, and `public/llms.txt` — this was a deliberate choice, not a placeholder. Don't reintroduce the numeric prices to the public-facing content without checking first.

## Enquiry & review notification email

`supabase/functions/notify-new-submission/index.ts` is a single Edge Function invoked by two plain SQL triggers (`supabase/migrations/20260802_notify_new_submission_trigger.sql`, one on `enquiries` INSERT, one on `reviews` INSERT via `pg_net.http_post`) — it branches on the `table` field it's sent, and emails `NOTIFY_TO` (three recipients: the practitioner, the business inbox, and the developer — real addresses only live in the deployed function, not this repo, see below) via Resend either way, sending from `enquiries@cmearwaxremoval.co.uk` (verified sending domain in Resend). **Not** the dashboard's Database Webhooks UI — that failed on this project (`schema "supabase_functions" does not exist`, never provisioned), so it's wired up as a raw trigger instead. Deployed and confirmed working end-to-end for both tables (`200` from Resend, real emails delivered to all recipients) — see README for the verification query. Unlike restore-relax, this had to be written fresh since restore-relax's equivalent function isn't in git and can't be copied directly.

## Admin panel login allow-list

Four identities can sign in to `/admin.html` and bypass RLS on `reviews`/`enquiries` (magic link via `auth.email() in (...)` on all six `Admins can ...` policies). The list was expanded live via the SQL Editor (`alter policy ... using (...)`), not committed as a migration — a migration file would need to contain the actual admin email addresses in this public repo. Two of the four are also in the Edge Function's `NOTIFY_TO` list above, but that's a separate, lower-stakes list (who gets emailed) — don't assume the two lists are the same when editing either one.

Never embed the `RESEND_API_KEY` in client-side code (`src/`) — this is a public repo on a static GitHub Pages site, so anything shipped to the browser is extractable by anyone. The key must only ever live server-side, as a Supabase Edge Function secret.

## Security review (2026-08-02)

A full pentest was run against the live site and Supabase backend. One real vulnerability was found and fixed; one apparent P0 turned out to be a false alarm from testing methodology, worth remembering:

- **Fixed — reviews moderation bypass.** `"Public can submit reviews"` originally had `with check (true)`, so an anonymous insert could set `status: "approved", approved: true` directly and appear live on the site immediately, skipping admin moderation entirely. Verified exploitable live (a fake review was inserted and confirmed publicly visible), then fixed via `alter policy ... with check (status = 'pending' and approved = false)` — anonymous submitters can no longer self-approve. Same hardening was **not** needed on `enquiries` (no `status`/`approved`-style privileged fields to escalate).
- **False alarm, not a bug — `RETURNING`/`return=representation` against a table with no public SELECT policy always raises the RLS-violation error, even when the INSERT itself succeeds.** Postgres treats `INSERT ... RETURNING` as requiring the new row to also be visible under the table's SELECT policies; if it isn't, it raises the exact same `"new row violates row-level security policy for table X"` error as a genuinely-blocked write — indistinguishable by error text alone. `enquiries` has no public SELECT policy (correct — enquiries are admin-only to read), so any INSERT test that asks for the row back (`RETURNING *` in SQL, or the `Prefer: return=representation` header PostgREST uses when a request wants the row) will *always* fail this way regardless of the INSERT policy, even a trivial `with check (true)`. This cost significant debugging time mid-pentest chasing a "broken contact form" that never existed. **If a plain anonymous INSERT looks RLS-blocked, retest without requesting the row back before concluding the write path is broken** — `ContactForm.tsx`/`Reviews.tsx` never call `.select()` after `.insert()`, so the app itself was never affected.
- Other findings, accepted as-is (low severity / platform limitations): `'unsafe-inline'` present in `script-src` on all three CSP entry points; `index.html`'s CSP is missing `frame-ancestors 'none'` (present on `admin.html`/`auth-confirm.html`); GitHub Pages doesn't set HTTP-level security headers (HSTS/X-Frame-Options/etc.), so hardening is CSP-meta-tag-only; `notify-new-submission`'s Edge Function URL is public (committed in this public repo) and accepts any well-formed `{table, record}` payload with the public anon key — someone who finds the URL could trigger arbitrary-content emails to all `NOTIFY_TO` recipients. Not remediated (would need a shared-secret header check in the function, verified by the SQL trigger).

**Follow-up pass, same day, via Supabase's Advisors (Database → Advisors):**

- **Fixed — `public.notify_new_submission()` had a mutable `search_path` while running `SECURITY DEFINER`.** Classic search-path-injection surface (a `SECURITY DEFINER` function without a pinned `search_path` can be tricked into resolving unqualified identifiers to attacker-created objects). Fixed with `alter function public.notify_new_submission() set search_path = ''` — safe here since the function's only external call, `net.http_post(...)`, was already schema-qualified. Also revoked direct `EXECUTE` from `public`/`anon`/`authenticated` (`revoke execute on function public.notify_new_submission() from public, anon, authenticated`) — it should only ever run via the two `AFTER INSERT` triggers, never as a direct RPC call. Verified both triggers still fire correctly after the change (fresh `200` in `net._http_response`).
- **Not a bug — Advisor flags `"Public can submit enquiries"` as "RLS Policy Always True".** Expected: it's a public contact form with no privileged fields (no `status`/`approved`-equivalent on `enquiries`) to escalate, unlike the `reviews` case above. Left as `with check (true)`.
- **Not actionable — "Leaked Password Protection Disabled".** Gated to Supabase's Pro plan; this project is on the free tier so the toggle is unavailable regardless. Low priority anyway since admin auth is magic-link only — password auth is never actually used.

**Follow-up pass, same day, via GitHub Dependabot alerts:** 4 open alerts (2 critical, 2 medium), all `minimist` prototype-pollution, all `development`-scope. `pnpm why minimist` traced both vulnerable versions to `html-inline` (a `devDependency` that was never actually invoked anywhere — not in `package.json` scripts, not referenced in any source file; likely leftover from the original restore-relax clone). **Fixed by deleting the unused dependency** rather than trying to force a transitive version bump — removed `html-inline` from `package.json`, ran `pnpm install` to regenerate the lockfile (25 packages dropped, `minimist` gone entirely), and confirmed both the `vite build` and the real production `parcel build index.html admin.html --dist-dir bundle-out --public-url "./"` still succeed unchanged.
